## Course overview

This course is a rigorous introduction to computer programming and computer science. This class does not presume any previous programming experience whatsoever. Although you will learn how to write effective and well-designed programs in the Python programming language in this class, Python is not the point of the class -- the point is using Python to get practice in the types of algorithmic thinking that will be useful throughout your careers as computer scientists and computer engineers, whatever languages you may work in or tools you may use.

Even though this is an introductory class, it is **not** designed to be an easy class. The pace of the class is very fast, by design.

You may initially find this material challenging and even frustrating. Programming is difficult at first, but by persevering you will learn many key concepts and skills that will be useful to you in almost all areas of computer science. It is completely normal to find yourself struggling with problems, and to think that these problems are impossible. The feeling of deep satisfaction you'll get when you figure out how to solve them more than makes up for the frustration you experience on the way.

## Student Learning Outcomes

Upon completion of this class, students will be able to do the following:

## Assignments

Because learning how to program well takes a large amount of practice, there are a relatively large number of assignments in this class. Toward the end of the semester there are fewer programs assigned, but each of these programs is longer.

In short: please only stay in this class if you are prepared to spend a *lot* of time on the assignments. I have had students tell me that they spend more time on the assignments for this class than for all of their other classes combined. This is by design. Learning to program is hard – it’s something like learning how to play a musical instrument -- and when starting out it is necessary to do a large amount of practice in order to build your intuition about what strategies work and what strategies don’t.

## Grading

### Grading overview

I generally despise giving tests; there is a large amount of very good research showing that learners tend not to retain information they learned while cramming for tests. As such, I've provisionally decided this semester to *not* have exams, and to make the entire grade derived from work on assignments. These assignments will be a mixture of short exercises and larger projects; generally the solutions to the short exercises flow directly into the projects -- what look like isolated solutions to contrived problems

### Functionality grading and style grading

Roughly 60% of your grade on each programming assignment is derived from your program’s *functionality*. If the output of your program in all cases matches the output of my version of the program, you will get full credit for functionality. You will lose points for functionality if I can find input that will make your program crash, produce invalid results, or otherwise fail to work correctly.

Roughly 40% of your grade comes from your code’s adherence to the *style guide* for the class. As you progress through your career as a programmer, you will find that using good code style makes your programs much, much easier to write, read, debug, and maintain. As such, it is crucial that you write stylistically sound code right from the start.

*Note: these are very rough guidelines, and the ratio for style grading and functionality grading will shift from assignment to assignment. In general, correct style and correct functionality can't be fully separated from each other, since using good code style will make it much easier to write code that works.*

### Late policy

Projects that are turned in a day or more before the due date get a 3% bonus. Projects turned in no more than 3 days after the due date get a 10% penalty. Projects turned in more than three days late get a 15% penalty.

## Academic Dishonesty and Cheating

Please carefully read the policies and contact me if something is unclear.

- It **IS** reasonable (and a good idea!) to discuss your ideas and your programs with your classmates.
- It is **NOT** reasonable to directly copy solutions from your classmates.
  - To avoid accidentally ending up with code that looks copied, I recommend that you avoid looking directly at each other's code. Talk about how your code works, think up ideas to improve your code, but don't **show** your code.
- It is **NOT** reasonable (or a good idea) to copy-paste code from Stack Overflow or other similar sites.
  - If you must use a *short* snippet of code from the Internet -- one or two lines at most -- **include a comment indicating where you got it from and how it works.** I reserve the right to ask questions to make sure you understand the code you've used.
  - Likewise, LLM-generated code can contain very advanced concepts and constructs. I do not ban the use of AI tools for this class, but when you use LLM code **include a comment indicating that it's LLM generated** that **explains in your own words how it works**.
  - It is not a good idea to copy someone else's code and then make small tweaks to make it seem like original work. Renaming variables and shuffling lines around hides copying much less well than people think. If you're curious why, [this paper co-authored by Stanford CS professor Alex Aiken](http://theory.stanford.edu/~aiken/publications/papers/sigmod03.pdf) describes "winnowing," the algorithm behind MOSS, a widely used code-plagiarism detector. It's a genuinely elegant piece of algorithm design.

## Let's talk about LLMs

So there are some things LLMs are really really good at, and some things they're much worse at. They are *very very good* at certain types of student exercises -- anything that there's a large amount of publicly-available code for, which describes most intro programming assignments, including the ones in this class. They get noticeably less reliable when you're doing something that's:

- More complicated or more unusual than what's common on the internet
- In a less-commonly used programming language or library
- Dependent on details of a large codebase that they can't see all of at once

And when they fail in these situations, the failures are often *subtle*: code that looks right, runs, and is wrong in a way you won't catch unless you understand it.

**For my part:** I tend to use LLMs for certain rote/repetitive tasks -- I often use them to correct accessibility-related errors and formatting inconsistencies in slide decks.

As far as coding with them: I find them very useful for writing "boilerplate-heavy" code; for example, I "vibe-coded" the graphical user interface of the Karel the Robot tool that's on the class GitHub. Before this semester I used a text-based interface for this tool, because I could never quite find the time to write the JavaScript GUI. One reason I put it off until I could ask a machine to do it for me is that the part of the program that is the same in the text-based version as in the GUI version -- the code that actually interprets Karel commands -- is inherently interesting, and absolutely has to be 100% correct. On the other hand, I find the parts about getting (for example) the GUI text box pane to display in exactly the right place to be kind of boring, and it's okay if there are small problems with it. 

I am comfortable using the vibe-coded interface for the Karel tool, since it's not a huge disaster if there are glitches that I haven't noticed -- if they happen you can tell me about them and I can dive into the code to fix them. I wouldn't be nearly as comfortable trusting the vibe-coded interface if I intended other instructors to use it, since I'm certain it has meaningful errors that I haven't yet spotted.

Additionally: if I didn't understand JavaScript and its limitations, I would have had a much harder time with the vibe-coding itself -- getting good results from automated code generation tools requires being able to clearly and concisely describe the problem, and also describe what's important to get right. When you vibe-code with concepts you *don't* already understand, you'll often get something that works -- at first. The trouble starts when it stops working, or when it works on the inputs you tried but not on the ones you didn't, and you can't tell why or how to fix it. At that point you're asking a machine to fix code that neither of you really understands, and that loop can eat an enormous amount of time (and tokens).

This is to say: LLMs are good at the boring part, which is pretty cool, and they're good at getting things *almost* right, which is sometimes all you need, and they're good if you can describe *exactly* what you want them to do, which requires real knowledge.

One 2025 study (by the research group METR) found that experienced developers working on large projects they knew well were about 19% *slower* when using AI tools -- while believing they'd been about 20% *faster*. The tools have improved since then, and 2026-era industry estimates tend to find gains that are real -- but far more modest than expected. One big reason: reviewing generated code for subtle errors takes time, and it takes most of the same knowledge of computer science and computer engineering that writing the code yourself does.

In short: it's a very, very good idea to learn the underlying concepts instead of just letting LLMs write code for you, because once you start writing programs above a certain level of complexity you will run into serious problems if you don't actually understand what the LLM generates.
